# 需求质量检查 Skill

对需求文档进行系统性质量检查，基于通用需求质量属性和业务自定义检查表，输出结构化问题报告和改进建议。

## 输入格式

支持以下输入形式：
- 直接粘贴的需求文本
- Word / PDF / Markdown 文档（含流程图、原型截图）
- 图片（流程图、原型图）
- 以上格式的组合

## 检查流程

### Step 0：识别需求内容形式

在开始检查前，先判断需求内容的形式：

**情形 A：需求正文仅包含设计稿地址**

如果需求正文主体是一个或多个设计稿链接（蓝湖 lanhuapp.com、Figma figma.com、Axure、即时设计 js.design 等），则：

1. 使用 WebFetch 工具尝试获取设计稿页面内容
2. 若能获取到内容（页面标题、组件描述、标注文字等），将其作为需求内容进行后续检查
3. 若无法获取（需要登录、内容为空等），在报告中注明"需求正文为设计稿链接，无法自动读取设计稿内容，以下检查基于链接本身及上下文信息进行"
4. 对于"交互设计完整性"和"设计稿地址"两项检查，若设计稿链接有效可访问，视为已提供；若链接无法访问，标记为 ⚠️ 并建议确认链接有效性

**情形 B：需求正文包含正常文字描述（含或不含设计稿链接）**

按常规流程继续执行 Step 1。

---

### Step 1：理解需求内容

先通读全部输入内容，理解：
- 需求的业务背景和目标
- 涉及的功能模块和用户角色
- 文档结构和完整程度

#### Step 1.1：识别并理解需求中的图片内容（强制）

需求中常包含原型图、流程图、交互稿、表格截图等图片，**很多关键的文字说明、字段定义、交互细节、状态流转、UI 文案、跳转规则、运营商差异、计费规则等只存在于图片里**。在质量检查前必须完成图片识读：

1. **逐张读取图片**：对需求文档 / Markdown 中引用的每一张本地图片（含原型图、流程图、表格截图、UI 截图等），使用 Read 工具读取（具备多模态视觉能力，可直接识别图片内容）。
2. **提取图片信息**，作为后续 Step 2 / 3 检查的输入：
   - **文字说明与标注**：原型图上的文案、表格中的字段值、注释说明
   - **页面布局与组件**：按钮、输入框、列表项、弹窗、Toast、Tab、空态等
   - **交互细节**：点击 / 滑动 / 长按行为、跳转目标、输入限制、默认值、按钮可用态
   - **状态与流转**：空态 / 加载 / 成功 / 失败 / 异常态、流程图节点与分支
   - **配置 / 规则表**：运营商差异、版本差异、计费规则、白名单、字段约束等
3. **图片内容参与一致性 / 完整性 / 无歧义性检查**，发现以下问题必须输出：
   - 图片中的文案 / 字段名 / 状态名 与 正文描述不一致 → 一致性问题
   - 正文未提及但图片中给出了关键交互 / 规则 → 完整性问题（需确认是否正式约定）
   - 图片中的流程分支或异常态在正文未覆盖 → 完整性问题
   - 多张图之间互相矛盾（如 A 图为弹窗、B 图为 toast） → 一致性问题
   - 图片中文案存在歧义或与功能不符 → 无歧义性问题
4. **图片缺失 / 无法读取**：若文档引用了图片但本地文件缺失或无法解析，在报告中显式标注 ⚠️"图片 {文件名} 无法读取，可能遗漏关键交互/规则"，**不要静默跳过**。

> 后续 Step 2 通用质量属性检查、Step 3 业务自定义检查表，必须把图片中提取到的信息纳入评审范围；不能仅基于正文文字判断"未提及"，否则会把图片里实际写明的内容误判为缺失。

### Step 2：通用质量属性检查

按照 `references/general-quality-attributes.md` 中的 7 个维度逐一检查。

对每个维度：
1. 判断是否存在问题（有问题 / 无问题 / 不适用）
2. **仅当有问题时**，输出一句话定性结论 + 置信度（高/中/低）
3. 具体缺失项不在维度中展开，统一归入 Step 3 业务检查表
4. 无问题和不适用的维度 → **不输出**

维度问题的来源标记为 🧠推理/正确性（依据 7 维度逻辑推断），推理类问题必须引用原文。

### Step 2.5：词法异味扫描（确定性检查）

按照 `references/requirement-smells.md` 逐条扫描需求正文与图片文字，检出模糊副词、最高级无基准、否定式、指代不清、漏洞措辞、TBD 待定等词法异味。

- 命中且结合上下文确认构成问题的，输出为一条问题：**来源 🔤规则命中(词法异味)、置信度默认高**，必须引用原文 + 给建议改写。
- 命中但上下文已给出精确定义/已消解歧义的，**不输出**。
- 优先级：多数属 🟢低/🟡中；出现在关键计费/权益/核心流程描述上时升为 🔴高。

### Step 3：业务自定义检查表检查

按照 `references/custom-checklist.md` 中的检查项逐一核对。

对每个检查项：
1. 判断结果：已提供 / 未提供 / 不需要
2. **仅输出"未提供"且该需求场景下应该提供的项**，标记为问题并说明原因
3. 已提供（✅）和不需要（➖）的检查项 → **不列出**
4. 若某个分类下所有检查项均通过或不适用 → **该分类整节不输出**
5. 来源标记为 📋知识库（业务检查表沉淀）；给出置信度（见下方说明）

### 置信度评估规则（高/中/低 三档）

每个问题输出一个置信度标签，表示 AI 对该条结论的确定程度：

| 置信度 | 含义 | 典型场景 |
|-------|------|---------|
| 高 | 有明确依据 / 规则命中 | 需求正文直接提及或明确缺失；词法异味等确定性命中 |
| 中 | 有一定依据但存在推断 | 需求描述不完整，部分内容需推断 |
| 低 | 信息不足，**建议人工确认** | 需求正文过于简略、仅有设计稿链接、关键上下文缺失 |

**低置信的常见原因**：
- 需求正文信息量不足（如仅有设计稿链接）
- 检查项依赖的业务背景未在需求中说明
- 需求描述存在歧义，结论依赖主观判断

> 低置信问题在标题旁标 `建议人工确认`，不下定论。

### Step 4：输出检查报告

使用下方的报告模板输出结果。

## 报告模板

> 注意：本 skill 通常被 `req-review-agent` 编排调用，最终报告结构以 `req-review-agent` 模板为准。下方模板为单独使用本 skill 时的输出格式，同样为**问题驱动、不使用表格**。

`````markdown
# 需求质量检查报告

## 一、给产品的核心建议
（3-5 条最重要的改进 action item，按优先级排列，用【必改】/【建议】各一句话说清问题+建议）
1. 【必改】…
2. 【建议】…

---

## 二、问题清单

> 来源：🧠推理/正确性 ｜ 🔤规则命中(词法异味) ｜ 📋知识库(检查表) ｜ 📌历史问题参考(尽力)
> 置信度：高 / 中 / 低（低置信 = 建议人工确认）
> 只输出有问题的项；某优先级下无问题则该分组省略。

### 🔴 高优先级（阻塞评审）

**RP-01 [问题一句话标题]**　📋知识库 ｜ 完整性 ｜ 置信度:高
- **原文/现状**：[引用原文 或 "未提及"]
- **问题**：[具体问题 + 影响]
- **建议改写**：[可落地补充/改写话术]

### 🟡 中优先级（影响开发理解）

**RP-02 [标题]**　🧠推理/正确性 ｜ 一致性 ｜ 置信度:中
- **原文/现状**：…
- **问题**：…
- **建议改写**：…

### 🟢 低优先级（完善性建议）

**RP-03 [标题]**　🔤规则命中(词法异味) ｜ 无二义性 ｜ 置信度:高
- **原文/现状**：“…”
- **问题**：…
- **建议改写**：…
（低置信项标题旁标 `建议人工确认`）
`````

- 7 维度的定性结论并入问题清单（标 🧠推理/正确性），不单列维度概览表。
- 词法异味命中标 🔤规则命中、置信度高；业务检查表缺失标 📋知识库。

### 行文要求

- 直接给事实和建议，不写"该需求整体表现良好"等套话
- 每条建议需可执行，避免泛泛而谈
- 引用原文要精确，帮助作者快速定位

---

## 注意事项

- 检查时结合需求的实际业务场景判断，不要机械套用所有检查项
- 引用原文时尽量精确，帮助作者快速定位
- 建议要具体可操作，避免泛泛而谈
- 自定义检查表支持动态扩展，如用户提到新增检查点，在本次检查中纳入并在报告末尾注明
- **不输出无问题的项**：通过和不适用的维度/检查项一律省略，不写"该维度表现良好"等套话
