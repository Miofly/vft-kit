# 活动宣传类需求专项检查

基于历史需求评审问题提炼的活动类专项检查点，配合通用检查（req-quality-check）使用。

## 执行说明

1. 先通读需求文档，理解活动的整体目标和业务背景
2. **逐张读取需求中的图片**（活动主页原型、抽奖 / 签到流程图、奖品配置表、规则截图、文案截图等），用 Read 工具识别其中的活动时间、规则文案、奖品规则、用户资格、状态流转、跳转规则等。**活动需求的活动规则和奖品发放细节经常完全写在图片里**，必须把图片信息纳入下方各项检查；仅依据正文文字判断"未提及"会误判为缺失
3. 按以下各维度逐项检查，结合实际需求判断是否适用
4. 检查结果标记：✅已提供 / ❌未提供（需补充）/ ➖不适用（说明原因）
5. 最后加载 `references/custom-checklist.md` 中的活动类自定义检查项，一并执行

## 输出规则（与 req-review-agent 编排时遵守）

- **只输出有问题的检查项**：✅已提供 和 ➖不适用 的项一律不展示
- **去重**：本专项检查只关注活动类业务独有的检查点；通用业务场景（页面交互/列表/输入框/登录等）已由 req-quality-check 业务检查表覆盖，本节不重复输出
- 若所有检查项均通过或不适用 → 整节不输出
- 直接给事实和建议，不写套话

## 内置检查点

### 一、时间规则
| 检查项 | 检查内容 |
|--------|---------|
| 活动时间 | 活动开始/结束的具体时间点是否明确（含日期、时分秒） |
| 时区说明 | 是否说明时区（默认北京时间，跨地区活动需特别标注） |
| 预热期 | 活动开始前的预热页面/状态是否说明 |
| 结束后状态 | 活动结束后页面展示什么内容，是否说明；需求需明确说明活动到期的具体时间，以及活动到期之后的下线展示样式 |
| 跨零点计算 | 涉及"当天"计算时，跨零点的处理规则是否定义 |

### 二、用户资格
| 检查项 | 检查内容 |
|--------|---------|
| 参与条件 | 参与资格条件是否明确（运营商/套餐/新老用户/地区限制） |
| 新老VIP区分 | 大多数活动针对新老VIP处理逻辑不一致，活动参与资格里面需要说明清楚（是否新VIP用户、新老VIP的权益差异） |
| 次数限制 | 同一用户的参与次数/领取次数上限是否说明 |
| 黑白名单 | 是否需要黑名单/白名单机制，规则是否定义 |
| 未登录用户 | 未登录用户如何处理（引导登录/直接参与） |

### 三、奖励规则
| 检查项 | 检查内容 |
|--------|---------|
| 奖励类型 | 奖励的具体类型和内容是否明确（积分/会员/数字内容/实物） |
| 库存上限 | 奖励总库存是否设定，超发如何处理 |
| 发放时机 | 奖励发放时机是否说明（实时/T+1/人工审核后） |
| 奖励有效期 | 发放后的奖励有效期是否定义 |
| 发放失败处理 | 奖励发放失败时的补偿方案 |

### 四、并发与限流
| 检查项 | 检查内容 |
|--------|---------|
| 峰值流量 | 活动预估峰值流量是否评估 |
| 限流方案 | 是否需要排队/限流/降级机制 |
| 超库存提示 | 奖励耗尽时的用户提示文案是否定义 |

### 五、多端适配
| 检查项 | 检查内容 |
|--------|---------|
| 端覆盖清单 | Web/App/小程序各端是否逐一说明是否参与 |
| 上线渠道 | 需要说明活动上线渠道和厂商（如移动/联通/电信，OPPO/VIVO/华为等） |
| 渠道差异 | 不同运营商渠道的活动差异是否说明 |
| 分享功能 | 是否涉及分享，分享内容/卡片样式是否定义；不同厂商分享特性不同，有些支持图片分享，有些不支持图片分享（因此需要考虑厂商特性） |

### 六、合规与风控
| 检查项 | 检查内容 |
|--------|---------|
| 防刷机制 | 是否有防刷/反作弊机制 |
| 法务审核 | 活动规则文案是否需要法务确认 |
| 数据统计 | 活动核心统计指标是否定义（UV/参与人数/转化率等） |

### 七、降级与应急
| 检查项 | 检查内容 |
|--------|---------|
| 提前结束 | 活动提前下线的处理方案 |
| 依赖降级 | 依赖服务不可用时的降级逻辑 |
| 应急开关 | 是否需要紧急暂停活动的配置开关 |

### 八、活动规则与流程合理性

> **与前7个维度的区别**：前7个维度检查"信息是否提供"（完整性），本维度检查"已描述的规则是否逻辑正确"（合理性）。即使信息齐全，规则本身也可能存在矛盾、死路径或未定义的叠加场景，本章节作为重点检查环节。
>
> **检查方式**：需要通读需求全文后进行逻辑推演，而非逐项核对是否存在。仅当发现实际问题时输出，无问题则整节不输出。

| 检查项 | 检查内容 |
|--------|---------|
| 规则自洽性 | 需求中不同位置对同一事物的描述是否存在矛盾。重点关注：1）数量/比例描述是否前后一致（如推荐歌曲数、概率加总是否100%）；2）同一概念的命名是否统一（如人格标签在不同章节的名称）；3）条件/门槛描述是否冲突（如A处说"免费参与"B处说"需订购解锁"） |
| 算法/映射完备性 | 涉及匹配、计算、随机等逻辑时：1）所有输入组合是否都能产出有效结果，有无死路径（如答题映射是否覆盖全部选项组合）；2）是否存在不可达的结果（如某种人格在算法上永远无法被命中）；3）平局/边界情况的兜底规则是否明确且无歧义；4）极端输入（全选同一选项、最短/最长路径）是否产出合理结果 |
| 用户动线闭环 | 用户从进入活动到完成目标的完整路径是否存在断点：1）是否有"去了回不来"的页面（如跳转外部页面后无法返回活动）；2）中途退出再进入时的状态恢复逻辑是否定义（如答题答到一半退出）；3）解锁/门槛条件是否清晰可达，用户是否能理解如何满足条件；4）流程中的"隐藏→恢复"等可逆状态，用户是否有明确的操作指引 |
| 状态叠加与冲突 | 用户多次参与或状态变更时是否存在未定义场景：1）重复参与时历史结果如何处理（覆盖/累加/共存）；2）已解锁权益在条件不再满足时的处理（如退订后解锁内容是否收回）；3）多次操作产生不同结果时的优先级规则（如测两次得到不同人格，以哪次为准）；4）并发操作（如同时在两个设备参与）是否有冲突处理 |

## 输出格式

以**问题驱动**方式输出本专项检出的问题（**不使用表格**），供 `req-review-agent` 汇入统一「问题清单」。单独使用时追加在通用检查报告之后。

- 只输出有问题的检查项；✅已提供、➖不适用一律不展示；无问题则整节省略。
- 每条问题：来源统一标 **📋知识库(活动类专项)**，置信度 高/中/低，含 原文/现状、问题、建议改写。

```
---

## 活动类专项检查结果（仅列有问题项）

**[问题一句话标题]**　📋知识库(活动类专项) ｜ 时间规则 ｜ 优先级:🔴 ｜ 置信度:高
- **原文/现状**：[引用原文 或 "未提及"]
- **问题**：[具体问题 + 触发条件/影响]
- **建议改写**：[可落地补充/改写话术]
```
