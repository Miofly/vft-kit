# 混合流程：共用证据记录、评审与交付

本文件把已采纳的四个来源连成同一条工作流，不另建互相竞争的写作模式。按本次交付从对应阶段进入，满足该阶段退出条件即可；只找文献不运行整套论文生产流程。

## 阶段与衔接

| 阶段 | 使用的输入与做法 | 交给下一阶段的材料 | 退出条件 |
|---|---|---|---|
| 定范围 | 读取用户附件、学校要求与真实研究条件；区分计划/实施 | 研究问题、交付范围、要求与证据缺口 | 请求没有被扩成另一个任务，规范冲突已标记 |
| 建证据 | 多库检索、去重、核验全文与元数据；整理实际数据 | 来源表、主张证据记录、阅读状态 | 每项来源状态明确，不把网页/摘要当全文 |
| 建论证 | 从材料中的问题出发选理论；凝练问题—改变—证据—边界 | 每章问题、论点、支持/反对证据、理论落点 | 章节形成递进链，创新措辞未超过证据 |
| 写草稿 | 按学校或学科结构，以证据提纲组织段落 | 正文、引用、图表与遗留缺口 | 草稿没有新造事实；范围内可写的部分已完成 |
| 分视角评审 | 按下节依次复核，不要求多 agent 或外部模型 | 有位置与依据的问题表及实际修订 | 事实变化同步引用、摘要、图表和结论 |
| 交付 | 内容证据、引用、格式与隐私分别过闸 | 用户要求的正文/文件与未核验说明 | 只在对应闸门满足后声明该层完成 |

融合分工：K-Dense 负责证据与写作顺序；humanities-thesis 负责材料、理论与章节递进；Chinese Thesis Workbench 负责规范、证据和图表追溯；Orchestra 负责贡献与证据主线。本地补充统一记录、离线检查与逐视角复核，不复制未采纳工具链。

## 最小共用记录

短任务直接用已有表格或工作笔记，不强制生成文件。多章写作/修订复用同一份记录，不让每章独立发明来源和事实。

- **要求**：要求 ID、原文件/条款、目标章节、检查状态。规范优先级以实际学校文件和导师明确指示为准，样文仅供参考。
- **来源**：稳定 ID、真实题名/作者/年份、DOI/地址或本地材料定位、核验状态、阅读状态。用户自己的数据记录与公开文献分开标识。
- **主张**：稳定 ID、正文位置、具体主张、类型（文献结论/真实观察/设计建议）、证据来源及页码/表号、待核实项。设计建议不能冒充观察结果。
- **图表**：编号、实际文件、数据/文献来源、正文引用位置、示意或实测、授权状态。图表内容改动回查受影响主张。
- **修订**：问题 ID、原文位置、依据、严重性、所改位置、复核结论。不记录不存在的评审人、签名或“七位专家一致通过”。

若需要机器检查，可用 [记录模板](../assets/evidence-ledger.json)，字段约定见下节；模板不是引用格式，不必把正文改成机器标记。

## 离线检查：只核对记录，不证明学术真实性

用当前 skill 的绝对目录表示 `SKILL_DIR`，`LEDGER_PATH` 为用户论文记录的绝对路径：

```bash
python3 -I "$SKILL_DIR/scripts/check_evidence.py" "$LEDGER_PATH"
```

脚本只读指定 JSON、输出 JSON，不访问网络、不改论文、不安装依赖。退出码：0 记录检查通过；1 有阻断问题；2 输入格式/类型不合法。`draft` 下允许未完成证据并输出 warnings；`final` 将其视为阻断。无论哪个阶段，重复 ID/DOI、断开的证据关系或无定位的“已支持”主张都阻断。

模板顶层：`stage`（draft/final）、`title`、`sources`、`claims`、`requirements`、`review`。所有数组显式存在，不能靠漏字段绕过检查。

- sources：`id`、`title`、`kind`（literature/policy/data）、`verified`（布尔）、`read_state`（record/abstract/fulltext）、`location`（非空来源定位），可选 `doi`。数据用原始记录/数据表路径或编号定位；`fulltext` 对数据表示已读原始记录，不是已做统计验证。
- claims：`id`、`text`、`kind`（literature/observation/proposal）、`status`（supported/pending）、`evidence` 数组；每项证据有 `source_id` 和 `locator`。supported 的文献/观察主张需要至少一项可定位且核验过的来源，observation 需要已核验且已读原始记录的 data 来源，即使 draft 也不能用未读数据标 supported；proposal 可无证据，但必须在正文保留设计/建议口径。
- requirements：`id`、`text`、`status`（done/pending）。这里只记录当前阶段适用要求，不把不适用项编为已完成。
- review：`id`、`issue`、`status`（open/resolved）。空 review 表不能证明已审稿；final 记录要求至少一个真实复核条目，零问题的复核可用 issue 写明所核对范围及未发现问题，status=resolved。

final 还要求来源已核验、已读完整材料、至少一个非建议类主张、适用要求有记录且完成、评审问题全部关闭。缺证据时诚实保留 draft，不把状态改成 supported/done/resolved 来消除报错。

本节的 check_evidence.py 不解析 DOCX、LaTeX 或正文参考文献；另有 [正文与交付检查器](manuscript-and-delivery.md) 做有限结构预检。不验证证据是否真的支持主张，也不验证记录的布尔值是否诚实。文内引用与文后条目的对应、题名真实性、数字一致性仍须实际阅读核对。无需新增任何模型服务。

## 分视角评审与回修

同一执行者可以依次换视角，不能称独立评审；只有用户明确需要且宿主允许时才另开独立评审。

1. **领域与论证**：研究问题是否具体；理论有定义、适用理由和材料落点；章节不是并排摘要；是否处理反例，结论外推是否过远。
2. **方法与数据**：样本、工具、实施、缺失和分析可追溯；计划时态没有变成已实施；设计是否允许因果/显著性措辞。
3. **引文与诚信**：逐条回来源核对主张；摘要/二手引用限制明确；不伪造题名、页码、数据和伦理批准。
4. **结构与交付**：学校要求逐条有落点；文内/文后、图号/表号和正文对应；摘要结论与正文一致；隐私、AI 披露和版式状态真实。

问题表每条写“严重性—原文位置—问题—证据—修法—复核结果”。阻断：虚构/关键无证据/错误引用/隐私泄露；重要：方法不足、论证断裂、模板硬要求未满足；一般：措辞与排版细节。先修阻断，再重要，再一般，不用总分掩盖关键问题。

每轮只修有证据的问题，更新共用记录，然后回查受影响章节、摘要、图表与结论。连续两轮没有新增证据或未解问题需要外部资料时，标记剩余阻塞并交阶段稿，不无限自评，也不降低成稿标准。

## 分层交付状态

分别报告：证据与方法核验、引文核验、学校格式检查、文件可打开/渲染、隐私与披露。任一层未验不写全部完成。离线记录通过只说明关系和状态满足规则；不能作为学术真实性、学校认可、录用或查重结果的保证。
